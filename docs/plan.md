# BuildLog MVP 개발 계획

## 1. 계획의 목적

이 문서는 `spec.md`에 정한 기능을 어떤 순서로 개발할지 설명합니다.

처음 개발하는 과정에서 한 번에 너무 많은 내용을 다루지 않도록 작업을 작은 Phase로 나눕니다. 한 번의 작업에서는 Phase 하나만 진행하고, 확인 기준을 모두 통과한 뒤 다음 Phase로 넘어갑니다.

## 2. 개발 원칙

- `spec.md`에 없는 기능은 추가하지 않습니다.
- 화면은 React, 서버는 Python과 FastAPI로 만듭니다.
- 서비스 데이터는 Supabase 데이터베이스에 저장하고 자동 테스트에는 SQLite3를 사용합니다.
- 각 Phase가 끝날 때 자동 테스트와 직접 화면 확인을 함께 수행합니다.
- 확인에 실패하면 다음 Phase로 넘어가지 않고 현재 Phase만 수정합니다.
- 화면에서 버튼을 숨기는 것만으로 권한을 처리하지 않습니다. FastAPI 서버에서도 사용 권한을 검사합니다.
- 비밀번호와 비밀 설정값을 코드에 저장하거나 화면에 보여주지 않습니다.
- 실제 SQLite 테스트 파일, `.env`, `.venv`, 로그와 생성 파일은 Git 기록 대상에서 제외합니다.
- Git 초기화와 커밋은 별도 요청이 있기 전까지 수행하지 않습니다.
- 꼭 필요하지 않은 외부 패키지는 추가하지 않습니다.

## 3. 예정된 프로젝트 구조

실제 개발을 시작하면 현재 `backend/`, `frontend/`, `database/`, `docs/` 폴더를 사용합니다. 기존 폴더를 옮기거나 삭제하지 않습니다.

```text
buildlog/
├─ backend/
│  ├─ app/
│  │  ├─ main.py              # FastAPI 실행 시작점
│  │  ├─ api/                 # 회원, 기록, 공개, 소통 요청 처리
│  │  ├─ core/                # 설정과 공통 권한 처리
│  │  └─ db/                  # 데이터베이스 연결과 저장 처리
│  ├─ tests/                  # FastAPI 자동 테스트
│  └─ requirements.txt
├─ frontend/
│  ├─ src/                    # React 화면과 사용자 동작
│  ├─ public/                 # 화면에서 사용하는 공개 정적 파일
│  └─ package.json
├─ database/
│  └─ test_buildlog.sqlite3   # 테스트용 파일, Git 제외
└─ docs/
```

Supabase의 실제 데이터베이스는 인터넷에 있는 프로젝트에 두며, 실제 데이터베이스 파일을 `database/` 안에 만들지 않습니다. 테스트 데이터베이스 SQLite3와 Supabase를 각각 연결하는 구체적인 도구는 Phase 0에서 확인하고 정합니다.

## 4. 전체 개발 순서

| Phase | 만드는 결과 | 다음 Phase로 넘어가기 위한 핵심 조건 |
| --- | --- | --- |
| 0 | 개발 기준과 환경 확인 | 문서, 실행 환경, 연결 방식에 충돌이 없음 |
| 1 | 실행 가능한 FastAPI·React 뼈대 | 서버와 기본 화면이 각각 정상 실행됨 |
| 2 | 사용자 모델과 Supabase·SQLite3 연결 기반 | 데이터 저장 경로와 사용자 모델 테스트 통과 |
| 3 | 회원가입·로그인·닉네임 | 회원 기능과 접근 제한 테스트 통과 |
| 4 | 세 가지 기록의 데이터 구조 | 저장·재실행·제약 조건 테스트 통과 |
| 5 | 공부 기록 전체 흐름 | 공부 기록 기능만 단독으로 완성 |
| 6 | 할 일 전체 흐름 | 할 일 기능만 단독으로 완성 |
| 7 | 오류 기록 전체 흐름 | 오류 기록 기능만 단독으로 완성 |
| 8 | 공개 기록·공개 범위·공개 검색 | 비공개 유출 없이 공개 기능 동작 |
| 9 | 댓글 | 댓글 조건과 권한 테스트 통과 |
| 10 | 좋아요 | 중복 방지와 취소 테스트 통과 |
| 11 | 신고와 운영자 확인 | 신고 저장·중복 방지·운영자 권한 확인 |
| 12 | 반응형 화면과 공통 오류 처리 | 360px 이상 화면과 지정 브라우저 확인 |
| 13 | 전체 통합 확인과 실행 문서 | `spec.md`의 완료 조건 전체 통과 |

## 5. Phase별 상세 계획

### Phase 0. 개발 시작 전 기준 확인

#### 목표

코드를 만들거나 설치하기 전에 문서, 도구, 실행 환경을 확인합니다.

#### 작업

1. `frontend/PRD.md`, `docs/spec.md`, `docs/plan.md`의 기능 범위와 기술 선택이 서로 맞는지 확인합니다.
2. 첫 버전에서 만들지 않을 기능을 다시 확인합니다.
   - 이메일 확인
   - 비밀번호 찾기
   - 할 일 마감일과 중요도
   - 내 할 일 검색
   - 댓글 답글
3. 현재 설치된 Python, Node.js, 패키지 도구의 버전을 읽기 전용으로 확인합니다.
4. Python에서 SQLite3를 사용할 수 있는지 읽기 전용으로 확인합니다.
5. Supabase 연결 방식, 데이터 구조 변경 방법, 자동 테스트 도구의 선택지를 정리합니다.
6. React 개발 서버 주소, FastAPI 서버 주소, 데이터베이스 경로, 환경 변수 이름을 정리합니다.
7. 테스트 명령과 서버 실행 명령을 기록할 준비를 합니다.

#### 예상 변경 파일

- 필요하면 `docs/plan.md`에 확인 결과를 보완합니다.
- 필요하면 실행 환경 안내를 위한 `docs/setup.md`를 작성합니다.
- 이 단계에서는 코드, 패키지, 데이터베이스를 변경하지 않습니다.

#### 확인 방법

- 세 문서를 읽었을 때 기능 범위나 기술 선택에 충돌이 없는지 확인합니다.
- Python·Node.js 버전과 SQLite3 사용 여부만 읽기 전용으로 확인합니다.
- 패키지 설치, Supabase 연결, 데이터베이스 파일 생성이 아직 없음을 확인합니다.

#### 완료 조건

- 개발 환경과 기술 선택에 막히는 항목이 없어야 합니다.
- 아직 사용자가 정해야 할 연결 방식이나 도구 선택이 있으면 추천안을 먼저 공유하고 확인을 받습니다.
- 확인 결과를 공유하고 Phase 1 진행 여부를 확인합니다.

### Phase 1. FastAPI·React 프로젝트 뼈대 만들기

#### 목표

기능 없이도 FastAPI 서버와 React 화면을 각각 실행하고 서로 연결할 기반을 만듭니다.

#### 작업

1. `backend/.venv`에 Python 가상환경을 준비합니다.
2. 호환되는 FastAPI 실행 기반을 구성하고 정확한 패키지 버전을 `backend/requirements.txt`에 기록합니다.
3. `backend/app/main.py`에서 FastAPI 앱과 기본 상태 확인 경로를 연결합니다.
4. React 앱의 개발 및 빌드 설정을 준비하고 `frontend/package.json`에 필요한 패키지와 명령을 기록합니다.
5. React에서 기본 홈 화면을 보여주고 FastAPI 상태 확인 결과를 받을 수 있게 합니다.
6. 개발용 환경 변수는 환경에서 읽도록 준비합니다. 실제 비밀값은 코드나 문서에 넣지 않습니다.
7. 루트 `.gitignore`에 SQLite 테스트 데이터 파일 등 제외 규칙이 있는지 확인하고 필요한 경우 보완합니다.
8. 첫 단계에서는 Supabase 프로젝트 연결이나 데이터베이스 생성을 하지 않습니다.

#### 예상 변경 파일

- `backend/app/main.py`
- `backend/requirements.txt`
- `frontend/package.json`
- `frontend/src/`
- `frontend/public/`
- `.env.example`
- `.gitignore`

#### 확인 방법

- FastAPI 개발 서버가 오류 없이 시작되는지 확인합니다.
- React 개발 화면이 브라우저에서 보이는지 확인합니다.
- React에서 FastAPI 상태 확인 경로를 호출할 수 있는지 확인합니다.
- 360px 너비에서도 기본 화면이 겹치거나 잘리지 않는지 확인합니다.
- 비밀 설정값과 SQLite 테스트 파일이 Git 기록 대상에서 제외되는지 확인합니다.

#### 완료 조건

- FastAPI 서버와 React 화면이 각각 실행되고 서로 연결됩니다.
- 실제 데이터베이스 연결이나 기능 개발은 아직 하지 않습니다.

### Phase 2. 사용자 모델과 Supabase·SQLite3 연결 기반

#### 목표

이메일로 로그인할 사용자와 서비스·테스트 데이터베이스 연결을 준비합니다.

#### 작업

1. 사용자 정보를 저장할 데이터 구조를 설계합니다.
2. 이메일은 필수이며 중복되지 않게 합니다.
3. 닉네임은 필수이며 중복되지 않게 하고, 2~20자와 한글·영문·숫자·밑줄 조건을 적용합니다.
4. 비밀번호는 안전하게 저장할 수 있는 방식으로 처리합니다.
5. 서비스 실행은 Supabase 데이터베이스를 사용하도록 연결을 구성합니다.
6. 자동 테스트는 SQLite3를 사용하도록 서비스 연결과 분리해 구성합니다.
7. Supabase 접속 정보와 비밀값은 `.env` 같은 로컬 환경 설정에서 읽고 Git에는 포함하지 않습니다.
8. 사용자 모델과 데이터베이스의 첫 구조 변경을 적용하고 저장·조회 테스트를 작성합니다.

#### 예상 변경 파일

- `backend/app/db/`
- `backend/app/` 사용자 데이터 구조
- `backend/tests/`
- `backend/requirements.txt`
- `backend/.env.example` 또는 루트 `.env.example`
- 데이터베이스 구조 변경 파일
- `database/test_buildlog.sqlite3` (Git 제외)

#### 확인 방법

- 같은 이메일이나 닉네임을 중복으로 저장할 수 없는지 확인합니다.
- 닉네임 길이와 허용 문자를 확인합니다.
- 비밀번호 원문이 저장되지 않는지 확인합니다.
- 테스트가 SQLite3를 사용하고 서비스 설정은 Supabase를 가리키는지 확인합니다.
- 앱을 다시 실행해도 저장한 사용자 데이터가 남는지 확인합니다.

#### 완료 조건

- 사용자 데이터 구조와 두 데이터베이스 연결 경계의 자동 테스트가 통과해야 합니다.
- Supabase 접속에 필요한 비밀값은 사용자가 로컬 설정으로 지정하고, 채팅으로 전달하지 않습니다.

### Phase 3. 회원가입·로그인·닉네임 변경

#### 목표

사용자가 계정을 만들고 로그인한 뒤 자신의 닉네임을 바꿀 수 있게 합니다.

#### 작업

1. React 회원가입 화면과 FastAPI 요청 처리를 만듭니다.
2. 이메일 앞뒤 공백 제거와 이메일 형식을 검사합니다.
3. 중복 이메일과 닉네임, 비밀번호 8~64자, 닉네임 2~20자와 허용 문자를 검사합니다.
4. 회원가입 실패 시 이메일과 닉네임은 유지하고 비밀번호만 지웁니다.
5. 성공하면 로그인 화면으로 이동합니다.
6. 이메일과 비밀번호 로그인, 성공 후 내 기록 홈 이동을 구현합니다.
7. 로그인 실패 시 이메일은 유지하고 비밀번호만 지웁니다.
8. 로그인하지 않은 사용자의 기록 화면 접근을 FastAPI에서도 막습니다.
9. 계정 설정에서 닉네임을 변경하고 과거 공개 기록과 댓글에도 새 닉네임을 표시합니다.
10. 이메일 확인과 비밀번호 찾기는 만들지 않습니다.

#### 예상 변경 파일

- `backend/app/` 회원 요청 처리
- `backend/tests/` 회원 테스트
- `frontend/src/` 회원가입·로그인·계정 설정 화면
- `.env.example` (필요한 설정 항목 이름만)

#### 확인 방법

- `spec.md`의 회원가입, 로그인, 닉네임 경계값을 자동 테스트합니다.
- 성공·실패 후 이동 화면과 입력값 유지 규칙을 확인합니다.
- 로그인하지 않은 사용자가 기록 주소에 직접 접근해도 볼 수 없는지 확인합니다.
- 다른 사용자의 닉네임을 바꿀 수 없는지 확인합니다.

#### 완료 조건

- 회원 관련 자동 테스트와 직접 화면 확인이 모두 통과해야 합니다.
- 이메일 확인과 비밀번호 찾기 기능은 만들지 않습니다.

### Phase 4. 세 가지 기록의 데이터 구조

#### 목표

공부 기록, 할 일, 오류 기록을 Supabase와 테스트 SQLite3에서 다룰 수 있는 기반을 만듭니다.

#### 작업

1. 공부 기록 구조를 준비합니다: 작성자, 제목, 내용, 공개 여부, 작성·수정 날짜와 시간.
2. 할 일 구조를 준비합니다: 작성자, 제목, 완료 여부, 공개 여부, 작성·수정 날짜와 시간, 완료 날짜와 시간.
3. 오류 기록 구조를 준비합니다: 작성자, 오류 제목·내용, 해결 방법, 해결 여부, 공개 여부, 작성·수정 날짜와 시간, 해결 날짜와 시간.
4. 세 종류 기록의 기본 공개 여부를 비공개로 설정합니다.
5. 새 할 일은 미완료, 새 오류 기록은 미해결로 설정합니다.
6. 제목과 내용의 길이 제한과 상태 전환 규칙을 저장 단계에서 검사할 수 있게 준비합니다.
7. 사용자와 각 기록의 작성자를 연결합니다.
8. Supabase용 데이터 구조 변경과 SQLite 테스트 구조가 같은 규칙을 확인할 수 있도록 준비합니다.
9. 기본 데이터 저장·조회·상태 전환 테스트를 작성합니다.

#### 예상 변경 파일

- `backend/app/` 기록 데이터 구조와 데이터 접근 처리
- `backend/tests/` 데이터 구조 테스트
- 데이터베이스 구조 변경 파일
- `database/test_buildlog.sqlite3` (Git 제외)

#### 확인 방법

- 세 종류의 기록을 저장하고 다시 읽을 수 있는지 확인합니다.
- 기본 공개 상태와 완료·해결 상태가 맞는지 확인합니다.
- 할 일 완료·취소 시각, 오류 해결·미해결 시각과 해결 방법 처리를 확인합니다.

#### 완료 조건

### Phase 5. 공부 기록 기능 완성

### Phase 6. 할 일 기능 완성

5. 완료 시 날짜·시간을 저장하고 미완료로 되돌릴 때는 완료 날짜·시간을 지웁니다.
6. 작성자만 제목과 공개 여부를 수정하고 삭제 전 확인 후 삭제할 수 있습니다.
7. 수정 날짜·시간을 목록 항목에 표시합니다.

- 필터·정렬·완료 취소 시각 처리를 확인합니다.
- 다른 사용자의 상태 변경·수정·삭제를 FastAPI에서 거부하는지 확인합니다.

### Phase 7. 오류 기록 기능 완성

오류 기록 만들기, 해결 처리, 필터, 검색, 수정, 삭제를 끝까지 연결합니다.

#### 작업

1. 오류 제목 1~100자, 오류 내용 1~5,000자, 해결 방법 선택 입력(입력 시 1~5,000자)을 적용합니다.
2. 제목·내용·해결 방법의 앞뒤 공백을 제거하고 중간 띄어쓰기는 유지합니다.
3. 새 오류는 미해결·비공개로 저장하고 해결 방법은 비워둘 수 있게 합니다.
4. 해결 상태로 바꾸려면 해결 방법을 필수로 하고 해결 날짜·시간을 저장합니다.
5. 미해결로 되돌릴 때 해결 방법은 유지하고 해결 날짜·시간을 지웁니다.
6. 전체·미해결·해결 필터, 최근 작성순 목록, 제목·내용 검색을 제공합니다.
7. 작성자는 수정·삭제할 수 있고 수정 날짜·시간을 상세 화면에 표시합니다.
8. 삭제 전 확인하고 저장 실패 시 입력값과 기존 데이터를 유지합니다.

#### 확인 방법

- 각 입력 길이 경계와 공백 처리를 테스트합니다.
- 해결 방법 유무에 따른 상태 전환과 날짜 처리를 확인합니다.
- 필터·검색·수정·삭제 및 작성자 권한을 확인합니다.

#### 완료 조건

- `spec.md` 오류 기록 관련 확인 항목이 모두 통과해야 합니다.

### Phase 8. 공개 범위·공개 기록·공개 검색

#### 목표

비공개 기록을 보호하면서 로그인 사용자에게 공개 기록을 제공합니다.

#### 작업

1. 작성자만 세 종류 기록의 공개 여부를 바꾸게 합니다.
2. 로그인한 사용자가 공개 기록 화면을 열고 공부 기록·할 일·오류 기록을 종류별로 볼 수 있게 합니다.
3. 공개 공부 기록은 제목·내용, 공개 할 일은 제목, 공개 오류 기록은 오류 제목·내용·해결 방법으로 검색합니다.
4. 빈 검색어는 전체 공개 목록을 보여줍니다.
5. 내 공부 기록·오류 기록 검색 범위를 유지하고 내 할 일 검색은 제공하지 않습니다.
6. 비공개로 바꾸면 다른 사용자에게 기록과 기존 댓글·좋아요를 숨기되 데이터는 보존해 재공개 시 다시 보여줍니다.
7. 비로그인 사용자의 공개 기록 화면 접근을 막습니다.
8. 작성자 닉네임은 현재 값을 공개 기록에 표시합니다.

#### 확인 방법

- 작성자, 다른 로그인 사용자, 비로그인 사용자를 구분해 접근 권한을 확인합니다.
- 세 종류 공개 검색의 검색 항목과 비공개 데이터 제외를 확인합니다.
- 비공개 전환 시 댓글·좋아요 숨김과 재공개 시 복원을 확인합니다.
- 기록 URL을 직접 입력해도 권한이 지켜지는지 확인합니다.

#### 완료 조건

- `spec.md` 공개·검색 관련 확인 항목이 모두 통과해야 합니다.
- 비공개 기록 노출이 하나라도 있으면 다음 Phase로 넘어가지 않습니다.

### Phase 9. 댓글 기능

#### 목표

공개된 공부 기록과 오류 기록에서만 댓글을 제공합니다.

#### 작업

1. 댓글 내용 1~500자를 적용하고 앞뒤 공백을 제거합니다.
2. 댓글을 오래된 순서로 보여주며 답글 기능은 만들지 않습니다.
3. 댓글 작성자는 자신의 댓글을 수정·삭제하고, 기록 작성자는 자신의 기록 댓글을 삭제할 수 있게 합니다.
4. 삭제 전에 확인하고 실패 시 입력값과 기존 저장값을 유지합니다.
5. 공개 할 일에는 댓글 기능을 제공하지 않습니다.
6. 기록을 비공개로 바꾸면 댓글을 삭제하지 않고 다른 사용자에게 숨겼다가 재공개 시 다시 보여줍니다.
7. 댓글에 작성자의 현재 닉네임을 표시합니다.

#### 확인 방법

- 댓글 길이 경계, 공백 처리, 오래된 순 정렬을 확인합니다.
- 댓글 작성자·기록 작성자·제3자의 수정·삭제 권한을 각각 확인합니다.
- 공개 할 일에는 댓글 기능이 없고 비공개 전환 시 기존 댓글이 숨겨지는지 확인합니다.

#### 완료 조건

- `spec.md` 댓글 관련 확인 항목이 모두 통과해야 합니다.

### Phase 10. 좋아요 기능

#### 목표

공개된 공부 기록과 오류 기록에서 사용자별 좋아요 등록과 취소를 제공합니다.

#### 작업

1. 사용자와 대상 기록 조합의 중복 좋아요를 막습니다.

3. 현재 사용자의 좋아요 상태와 전체 개수를 보여줍니다.
4. 등록·취소 실패 시 기존 상태를 유지합니다.
5. 공개 할 일에는 좋아요를 제공하지 않습니다.
6. 기록이 비공개가 되면 좋아요를 삭제하지 않고 숨기며, 재공개 시 다시 보여줍니다.

#### 확인 방법

- 중복 저장 방지, 등록·취소, 전체 개수를 확인합니다.
- 공개 할 일에 좋아요가 없는지 확인합니다.
- 비공개 전환 후 기존 좋아요와 개수가 숨겨지고 재공개 시 보이는지 확인합니다.

#### 완료 조건

- `spec.md` 좋아요 관련 확인 항목이 모두 통과해야 합니다.

#### 작업

- 신고 후 대상이 자동 삭제되지 않는지 확인합니다.

## 6. 실제 진행 방법

1. 첫 작업은 Phase 0만 진행합니다.
2. Phase 0의 확인 결과와 필요한 결정을 공유합니다.
3. 사용자가 확인하면 Phase 1만 진행합니다.
4. 이후에도 같은 방식으로 Phase 하나씩 진행합니다.
5. 여러 Phase를 한 번에 구현하지 않습니다.
